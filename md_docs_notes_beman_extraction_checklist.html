Checklist: Beman Reference Layout

Purpose

This checklist turns the Beman integration plan into a concrete reference layout.

It is intentionally narrower than the broader planning notes. Its job is to answer:

  • what the full reference implementation should expose
  • what public names should be used at extraction time
  • what belongs under the top-level public include tree
  • what belongs under detail/
  • which tests belong with each component
  • which examples belong with each component
  • what should remain in trees

This checklist assumes the current working Beman short name is:

  • structure

If that name changes, the checklist still mostly stands, but all target paths need to be rewritten.

Repository Bootstrap

  • choose the final Beman short name before moving code
  • stamp from a Copier-capable exemplar baseline
  • preserve .copier-answers.yml so later copier update --trust is possible
  • create the Beman repository with the final namespace, package, and target spellings already chosen

Public Naming Contract

  • confirm the public headers under include/beman/structure/
  • confirm which filenames use operation names rather than framework nouns
  • confirm that version suffixes do not survive in public headers
  • confirm which current wrapper names lose finger_tree_ in public headers
  • confirm that large structural helper code moves under include/beman/structure/detail/

Tests and Examples

  • move tests into tests/ with *.test.cpp naming
  • create top-level examples for the public headers
  • ensure examples use only the approved public include spellings
  • add tests for any detail/ headers that remain large enough to deserve their own factoring

More specifically:

  • every promoted public header must have at least one corresponding test target in tests/
  • every top-level capability header should have at least one runnable example or usage test demonstrating the intended public include spelling
  • every large detail/ header that exists because it is too large to inline must also have tests appropriate to that factored support surface
  • the reference layout should carry tests and examples with the component, not as a cleanup pass later

Completion Criteria for the Reference Layout

  • the Beman repo builds with the Copier-capable template baseline
  • the include tree exists under include/beman/structure/
  • the public API no longer exposes versioned finger-tree names
  • the public API no longer exposes adapter-split headers unless intentionally preserved
  • the front-door public API uses verb-first names where the paper plan now depends on them, especially traverse, transpose, fold, and apply
  • large support code lives under detail/ where appropriate
  • each promoted component has tests in the Beman repo
  • each top-level public surface has at least one example or equivalent usage demonstration in the Beman repo
  • tests and examples use only final public include spellings
  • exploratory and pedagogical variants remain in trees
