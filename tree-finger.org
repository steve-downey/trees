* One Data Structure, Many Meanings

- Finger trees are not just a data structure
- They are a *framework*
- Behavior comes from:
  - Monoid
  - Measure
  - Generic algorithms

#+begin_notes
Core message:
separate structure from interpretation

This is the same move as Liskov:
data abstraction > representation

The tree is fixed
meaning comes from the monoid
#+end_notes


* Fingertree Structure

#+begin_src mermaid
graph TD
  A[Empty] --> B[Single]
  B --> C[Deep]
  C --> D[Prefix Digit]
  C --> E[Middle Tree]
  C --> F[Suffix Digit]
#+end_src

#+begin_notes
Emphasize:
this is a 2-3 tree with slack at the edges

Digits are the buffer
Middle is recursive structure

Non-regular recursion:
type changes at each level
#+end_notes


* Deep Node Invariant

#+begin_src mermaid
graph LR
  P[Prefix] --> M[Measure]
  MID[Middle] --> M
  S[Suffix] --> M
  M --> T[Tree Measure]
#+end_src

#+begin_notes
Everything depends on this:

measure(prefix)
<> measure(middle)
<> measure(suffix)

If this breaks, everything breaks:
split, search, concat

This is the real data structure
not the pointers
#+end_notes

* Concatenation

#+begin_src mermaid
flowchart LR
  L[Left Tree] --> C[Concat]
  R[Right Tree] --> C
  C --> N[Node Packing]
  N --> T[New Tree]
#+end_src

#+begin_notes
Key insight:

concat is not trivial
it is the hardest operation

You must:
- take suffix of left
- take prefix of right
- pack into nodes

This is where amortized guarantees come from
#+end_notes


* Split/Search

#+begin_src mermaid
flowchart TD
  T[Tree] --> P[Check Prefix]
  P -->|match| SP[Split Prefix]
  P -->|no| M[Check Middle]
  M -->|match| SM[Split Middle]
  M -->|no| S[Split Suffix]
#+end_src

#+begin_notes
This is the superpower

We are not searching values
we are searching *measure*

predicate must be monotone

This generalizes:
indexing, priority queues, intervals
#+end_notes

Same structure

Important:

not member functions
