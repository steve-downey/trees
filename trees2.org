* Opening
** Slide: Why this talk exists
*** Goal
- Show that typeclass-style interfaces in C++ can be:
  - open for extension
  - law-oriented
  - optimizer-visible
  - practical on real tree structures
- Build an existence proof suitable for WG21 discussion and for live code.

*** Notes
- Start from the engineering problem, not category theory.
- Existing C++ gives us algorithms and customization points, but not a good, uniform vocabulary for higher-order structure like Foldable, Applicative, Traversable.
- The project is not recreate Haskell in C++.
- The project is use C++ mechanisms to encode the useful parts of these abstractions transparently.

*** Code hooks
- src/smd/concept_map/ existing material
- new top-level readme section introducing project purpose

** Slide: The core idea in one sentence
*** Claim
- A typeclass object is a named record of operations, found by variable-template lookup, and optionally supplied explicitly or as an NTTP.

*** Notes
- Emphasize:
  - lookup by type
  - no virtual dispatch
  - no heavyweight type erasure
  - explicit control when desired
- Distinguish this from ordinary ADL-based CPOs.
- The typeclass object is separable from the type.
- That separability is what makes open extension and alternate instances work.

* Part I: The concept_map machinery
** Slide: Dispatch modes
*** Bullets
- Implicit lookup via variable template
- Explicit map object parameter
- NTTP map object parameter
- Same semantics, different ergonomics and optimization surface

*** Notes
- Explain when each form is useful:
  - implicit: normal user-facing generic algorithms
  - explicit: testing, local overrides, law checks
  - NTTP: maximally static specialization and named instance style programming

** Slide: What lives in a typeclass object
*** Bullets
- Named operations, not tuple positions
- Operations may be derived from each other
- Minimal complete definition is part of the interface design
- Laws belong to the typeclass as much as signatures do

*** Notes
- This is where to connect to concept_maps.org.
- The point is not merely dispatch.
- The point is packaging a family of coherent operations and derived defaults.
- Similar in spirit to a record-of-functions, but with compile-time lookup and better composition with templates.

* Part II: Foldable
** Slide: What Foldable means here
*** Bullets
- A way to consume a structure into a summary
- Primary abstraction is monoidal accumulation
- Left and right folds are important operational views, not the semantic center

*** Notes
- Make the case that =fold_map= is the semantic primitive.
- =to_list= is derived, useful, but not fundamental.
- Connect to monoidal measures and finger trees early.

*** Code hooks
- src/smd/typeclass/foldable.hpp

** Slide: Minimal Foldable interface
*** Bullets
- Required:
  - =fold_map(F, X)=
- Derived:
  - =fold_left(F, init, X)=
  - =fold_right(F, init, X)=
  - =to_vector(X)=
  - =is_empty(X)= via fold/map or direct override
  - =length(X)= via monoid/counting
  - =contains_if(X, pred)=
  - =all_of= / =any_of=

*** Notes
- Explain why =fold_map= is the required core:
  - closest to laws
  - container-shape independent
  - naturally composes with measures
- Mention operational caveat:
  - some instances may override left/right folds for efficiency or stack behavior.

*** Code hooks
- src/smd/typeclass/foldable.hpp
- src/smd/typeclass/foldable.cpp
- src/smd/typeclass/foldable.t.cpp

** Slide: Foldable laws
*** Bullets
- Fold via monoid homomorphism must be coherent
- Derived folds must agree with =fold_map=
- Composition with monoid morphisms should preserve meaning

*** Notes
- Phrase laws as implementation constraints, not just math trivia.
- For tests:
  - =fold_map(id_as_monoid)= same as direct measure
  - counting via fold_map equals length
  - concatenating summaries respects tree concatenation
- Mention fusion/deforestation as a design payoff:
  - once generic algorithms are phrased through fold-like structure, derived traversals can avoid intermediate lists.

- src/smd/typeclass/monoid.t.cpp

** Slide: Foldable for trees
*** Bullets
- Tree-specific traversal order matters
- Pick one semantic order and make it explicit
- Other orders are separate views, not accidental overloads

*** Notes

  - inorder for binary search oriented trees?
  - left-to-right leaf order for finger/fringe trees?
- The law is not all orders are equal.
- The law is this instance has one coherent order.

* Part III: Applicative
** Slide: Why Applicative, not Monad
*** Bullets
- Independent structure-preserving combination
- Enough for traversal
- Better fit for trees and static composition
- More analyzable than bind-heavy designs

*** Notes
- Applicative is the key bridge between container with structure and effectful traversal.
- It is also where your chosen API differs from textbook Haskell.

*** Code hooks
- src/smd/typeclass/applicative.hpp

** Slide: Applicative API in this project
*** Bullets
- User-facing primitive: =invoke=
- Internal basis may still define =pure= and =apply= or equivalent
- Generic use should look like applying a pure function to effectful arguments

*** Notes
- Lead with your preferred surface:
  - =invoke(f, ax, ay, az)=
- Explain that this encodes:
  - lift a pure function into the applicative and feed it applicative arguments
- Say plainly that =ap= is not a good user API.
- If =pure= exists, it should mostly support derivation and laws.

*** Code hooks
- src/smd/typeclass/applicative.hpp
- src/smd/typeclass/applicative.cpp

** Slide: Minimal Applicative interface
*** Bullets
- Required option A:
  - =pure(x)=
  - =apply(af, ax)=
- Required option B:
  - =invoke(f, args...)= as primitive
- Derived:
  - =map=
  - =product(ax, ay)=
  - =lift2=, =lift3=, ...
  - =then_left= / =then_right=

*** Notes
- Recommend one internal normalization:
  - either define instance authors against =pure + apply=
  - or allow =invoke= as MCD and derive =apply=
- My recommendation for the code plan:
  - instance-level MCD remains =pure + apply=
  - public algorithm vocabulary centers on =invoke=
- That keeps law statements familiar while preserving your surface design.

** Slide: Applicative for trees
*** Bullets
- Need a concrete semantics:
  - zippy/shape-preserving
  - Cartesian/product-like
- Pick one instance as primary
- Additional semantics can be alternate maps

*** Notes
- This is an important design decision slide.

  - primary instance = shape-preserving zip-style applicative
- Why:
  - traversal and law checking are clearer
  - structure is respected
  - better fit for existence-proof code
- A Cartesian/tree-product applicative is interesting, but likely distracts from the main talk.

* Part IV: Traversable
** Slide: Traversable is the point where everything meets
*** Bullets
- Traversable = structure-preserving effectful walk
- Depends on Functor + Foldable + Applicative
- Gives one generic account of mapping with effects

*** Notes
- This is the abstraction that justifies the whole stack.
- Foldable gives summaries.
- Applicative gives effect composition.
- Traversable gives effectful structural transformation.

*** Code hooks
- src/smd/typeclass/traversable.hpp

** Slide: Minimal Traversable interface
*** Bullets
- Required:
  - =traverse(F, X)=
- Derived:
  - =sequence(X of applicatives)=
  - =mapM= style convenience aliases if desired
  - =for_each_accum= patterns via state-like applicatives
  - =map= from traverse + identity applicative
  - =fold_map= from traverse + const applicative, if useful

*** Notes
- =traverse= is the one real operation.
- Everything else should either be derived or explicitly justified as an optimization override.
- Mention representation theorem intuition:
  - traversable structures behave like a shape plus ordered positions.

- src/smd/typeclass/traversable.hpp

** Slide: Traversable laws
*** Bullets
- Naturality
- Identity
- Composition

*** Notes
- Express in engineering terms:
  - identity applicative gives identity transformation
  - composing applicatives agrees with single composed traversal
  - traversal does not invent or lose positions
- This is where you can mention finitary container intuition without going full theorem-proof.

* Part VI: Reflection and derivation
** Slide: What C++ reflection changes
*** Bullets
- Derive Functor/Foldable/Traversable from structure
- Use reflection to inspect fields and recursive positions
- Generated instances can still be ordinary concept_map objects

*** Notes
- Keep this as forward-looking, not core dependency.
- Main idea:
  - derive_* utilities synthesize the typeclass object
  - explicit customization points remain available for overrides
- Compare to GHC deriving:
  - structural, law-guided, with escape hatches

*** Code hooks
- provisional:
  - src/smd/typeclass/derive_functor.hpp
  - src/smd/typeclass/derive_foldable.hpp
  - src/smd/typeclass/derive_traversable.hpp

** Slide: Constraints on derivation
*** Bullets
- Need identifiable recursive positions
- Need variance checks for Functor
- Need ordered positions for Foldable/Traversable
- Some types need explicit override

*** Notes
- Be honest that automatic derivation is partial.
- Reflection helps, but does not remove semantic choices.
- Traversal order must still be chosen.
